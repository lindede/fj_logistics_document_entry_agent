## 2. 核心要求

### 2.1 多模态 / 非结构化数据解析

| 编号 | 原文要点 | 我方理解 | 优先级 | 实现注意 |
| --- | --- | --- | --- | --- |
| PAR-01 | 读取 BKG.pdf，提取字段为 JSON | 从 PDF 抽出字段表，输出结构化 JSON | P0 | `LLM_INPUT_MODE` 可配 pdf/vision/html/html_struct/html_mix；结构侧按版式家族分派（见 booking_parse_summary） |
| PAR-02 | 必填字段有直接对应 | 样例中一般能见到，应尽量抽出 | P0 | 见 FLD-01～15 |
| PAR-03 | 扩展字段无对应可留空 | 无证据则为 `null`（不是空字符串），不编造 | P0 | 唛头不得自填 `N/M`；见 FLD-16～18、BR-05 |
| PAR-04 | 期望 JSON 形态 | 类型与 key 以期望格式为准 | P0 | 表头 `Cargo` → 统一用 `goods_desc`（FLD-11） |

| 编号 | Key | 原文说明 | 我方理解 |
| --- | --- | --- | --- |
| FLD-01 | shipper | 发货人 | 托运/出口方 |
| FLD-02 | consignee | 收货人 | 收货方；可与发货人相同（见 BR-04） |
| FLD-03 | notify_party | 通知方 | 到港通知对象，常为货代 |
| FLD-04 | vessel | 船名 | 应有值 |
| FLD-05 | voyage | 航次 | 可 `""` |
| FLD-06 | port_of_loading | 装货港 | 港名+代码可在同一字段；不作跨字段「名对代码」 |
| FLD-07 | port_of_discharge | 目的港 | 同上 |
| FLD-08 | containers | 箱型/箱量 | 数组 `[{type, qty}]` |
| FLD-09 | packages_qty | 件数（纯数字） | number/int |
| FLD-10 | packages_unit | 包装单位 | 如 CTNS |
| FLD-11 | goods_desc | 品名（英文） | 原文表写 Cargo，JSON 用 goods_desc |
| FLD-12 | gross_weight | 毛重（纯数字） | 与单位分开存 |
| FLD-13 | weight_unit | 重量单位 | 如 KGS / TON；阈值见 BR-02 |
| FLD-14 | measurement | 体积（纯数字） | 与单位分开存 |

### 2.2 业务规则校验与数据治理

| 编号 | 原文要点 | 我方理解 | 优先级 | 实现注意 |
| --- | --- | --- | --- | --- |
| VAL-01 | 绝不允许编造或错误录入 | 无依据不填；失败不能当成功 | P0 | 与 BR-05、FLD-17 联动 |
| VAL-02 | 分层校验（五层） | Tool 内完成五层；Agent 校验网关只读报告分流 | P0 | 动态改数后要再跑规则（ADV-01） |
| VAL-03 | ① 输入验证与标准化 | 清洗 OCR/PDF 文本、统一格式 | P0 | |
| VAL-04 | ② 结构化输出控制 | 保证固定 JSON 与类型；缺 key 要结构补齐 | P0 | 按 FLD 补全全部 key，缺省值 `null`（不编造业务内容），便于界面编辑；见 DATA-* |
| VAL-05 | ③ 业务规则引擎 ≥3 条 | 确定性规则见 BR-* | P0 | |
| VAL-06 | ④ 人机协同与置信度 | FAIL/低置信度 → 人工；不静默成功 | P0 | 置信度细节见 ADV-02 |
| VAL-07 | ⑤ bad case → 回归用例 | 人工改过的错例可沉淀再跑 | P1 | |
| VAL-08 | 输出 raw / validated / report | 一次解析必须带齐三件套；report 含字段结果、置信度、建议操作 | P0 | 与 API-03 一致；会话内再包进 BookingRecord（DATA-01） |

**录入过程数据容器（澄清，便于全程追踪）**

| 编号 | 要点 | 我方理解 | 优先级 | 实现注意 |
| --- | --- | --- | --- | --- |
| DATA-01 | 会话/票数据外层记录 | 一票进行中的数据放在统一 **BookingRecord**（订舱记录）里，除三件套外含 `meta`、`history` | P0 | 与业务字段 `containers`（箱型箱量）不是同一概念 |
| DATA-02 | meta：字段来源 | `meta` 描述各字段来源；未标明时**默认 `llm`**（LLM 识别） | P0 | 人改后标 `human`；结构补齐产生的空位可标 `schema`/`system`；系统自动提交等可标 `system` |
| DATA-03 | history：编辑/过程历史 | 记录本票从开票到提交/作废的关键过程（解析、校验、改字段、提交等） | P0 | 按时间追加；至少含时间、动作、操作者（llm/human/system）、变更摘要 |

BookingRecord 形态（示意，非最终字段全集）：

```text
BookingRecord
├── session_id / status          # 会话状态
├── raw_extracted_data           # 三件套（业务字段层对应 BookingData）
├── validated_data
├── validation_report
├── meta
│   └── fields[field_key].source   # llm | human | system | schema …
└── history[]                    # { at, action, actor, detail/changes }
```


**已定业务规则**

| 编号 | 规则 | 级别 | 说明 |
| --- | --- | --- | --- |
| BR-01 | 装货港 ≠ 目的港 | FAIL | 跨字段；FLD-06 / FLD-07 |
| BR-02 | 毛重/体积数值范围随单位变化，且应 > 0 | FAIL | KGS 与 TON 上限不同 |
| BR-03 | 船名白名单：`vessel` 应在已知船名集合内 | 默认 WARN | 船名可收集、相对稳定；**不做**「船名+航次」绑定。未命中 → WARN + 人工，不硬拒绝 |
| BR-04 | shipper == consignee | WARN | 允许相同，只提示 |
| BR-05 | 扩展字段无证据 → `null` | 硬约束 | 不编造；含唛头；勿用 `""` 表示「没有」 |
| BR-06 | 港口白名单：`port_of_loading` / `port_of_discharge` 中的港名或代码应能匹配已知港口 | 默认 WARN | 同字段内校验（名/码或名+码）；可用 UN/LOCODE 等公开数据。未命中 → WARN + 人工，不硬拒绝 |

**明确不做（无编号，仅防误实现）：** 港名对代码跨字段；毛重/单位「成对出现」当业务勾稽；「有航次⇒必须有船名」。
